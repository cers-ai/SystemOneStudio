# GPU 节点运行手册

把这台机器搬到有 NVIDIA GPU 的节点上，按顺序执行。**先跑 doctor**，它会告诉你缺什么，别跳。

---

## 0. 前置检查（宿主机，不进容器）

```bash
nvidia-smi
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
```

两条都必须成功。第二条失败说明 NVIDIA Container Toolkit 没装，**后面所有步骤都不会成功**。

需要 ≥ 12GB 显存（需求 8.1：3B + LoRA 约 12GB，QLoRA 约 8GB）。低于 12GB 请改用 1.5B 底座。

---

## 1. 准备数据目录

```bash
export SON_DATA_DIR=/data/son          # 改成你的路径
mkdir -p $SON_DATA_DIR/{models,checkpoints,hf-cache,logs}
```

Windows 上路径形如 `D:/SystemOneStudio-data`，compose 已按 `${SON_DATA_DIR}` 读取。

---

## 2. 构建并启动

```bash
export SON_DATA_DIR=/data/son
docker compose -f deploy/gpu/docker-compose.gpu.yml up -d --build
```

首次构建会从源码编译 llama.cpp（约 10–20 分钟），并安装 torch CUDA 轮子（约 3GB）。之后有缓存。

```bash
docker compose -f deploy/gpu/docker-compose.gpu.yml logs -f gpu
```

---

## 3. 环境自检

```bash
docker compose -f deploy/gpu/docker-compose.gpu.yml exec gpu python -m son_cli doctor
```

输出 JSON，逐项列出：

| 项 | 期望 |
|---|---|
| `cuda_available` | `true` |
| `gpu[0]` | 你的卡名 + 显存 + `bf16` |
| `transformers` / `peft` / `trl` / `bitsandbytes` | 全部 `ok: true` |
| `llama-server` / `llama-quantize` | 找到路径 |

任一为 `false` 会同时列在 stderr 的「阻塞项」里，退出码非 0。

**把这段输出发给我**——它比任何推测都有用。

## 4. 训练

```bash
# 把你的种子数据放进容器，或挂载
docker compose -f deploy/gpu/docker-compose.gpu.yml exec gpu \
  python -m son_cli train \
    --dataset /data/son/data/seed.csv \
    --model qwen2.5-3b-instruct \
    --output-dir /data/checkpoints/run1 \
    --job-id mv_0017 \
    --qlora                 # 显存不够时加这个
```

数据需满足：

- 含一列 `black` / `white` / `gray`（或中文「黑/白/灰」）作为标签，列名任意可自动识别
- 至少一列特征字段
- **不含合成数据**：测试集会自动排除合成行，这条是硬约束

`--dpo` 会在 SFT 之后追加偏好对齐（需要足够样本产生正确/错误判定对）。

训练产物：`/data/checkpoints/run1/sft/`（LoRA 适配器）+ `run_manifest.json`（记录了底座、超参、样本数，用于版本追溯）。

---

## 5. 量化

```bash
docker compose -f deploy/gpu/docker-compose.gpu.yml exec gpu \
  python -m son_cli quantize \
    --adapter /data/checkpoints/run1/sft \
    --model qwen2.5-3b-instruct \
    --output-dir /data/son/models \
    --job-id mv_0017
```

产出 `mv_0017.Q4_K_M.gguf` / `.Q5_K_M.gguf` / `.Q8_0.gguf` + 合并权重，附 SHA256。

**顺序很重要**：先合并再转换。反过来（分别转换底座和适配器）会得到一个静默忽略训练结果的 GGUF。

---

## 6. 推理冒烟

```bash
docker compose -f deploy/gpu/docker-compose.gpu.yml exec gpu \
  python -m son_cli infer \
    --model /data/son/models/mv_0017.Q4_K_M.gguf \
    --gpu-layers 99
```

会启动 llama-server、发一次带 GBNF 约束的请求、打印 TTFT 与总耗时、然后停掉服务。

> 单次请求**不足以支撑 P95 结论**。正式压测需要并发压测工具，那是 M6 的工作。

---

## 7. 完整评测（要等 Q1 定案）

效果指标（准确率、召回、误杀率、F1、AUC、格式合规率）可以在本地算，不需要 GPU。

性能指标需要压测，且 **P95 ≤ 100ms 的口径尚未定案**（与 `reason` 200 字符上限冲突，见 `技术方案.md` Q1）。评测接口对 P95/P99 返回 `passed=null` 并注明原因，不会给出一个假的达标结论。

## 已知会踩的坑

**CUDA 版本不匹配** —— 镜像固定 `nvidia/cuda:12.4.1` + torch cu124 轮子。宿主机驱动过旧会报 `no kernel image is available`。查 `nvidia-smi` 右上角的 CUDA Version，需 ≥ 12.4。

**显存不足** —— 换 1.5B 底座，或加 `--qlora`。参考值：3B+LoRA 约 12GB，3B+QLoRA 约 8GB。

**`shm_size` 默认太小** —— compose 已设 8GB。DataLoader 报 bus error 时检查这一项。

**llama.cpp 编译耗时** —— 首次构建 10–20 分钟，属正常。
