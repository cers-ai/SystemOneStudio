# SystemOneStudio 开发计划

> 版本：v0.1（规划稿）
> 上游依据：`需求方案.txt` 第 12 章（落地路线图）、`技术方案.md`
> 配套文档：`AGENTS.md`（仓库约束与环境事实）

## 0. 计划原则

1. **先定口径，再写代码。** `技术方案.md` 的 Q1（P95 口径）、Q3（JEV 官方规范）是阻塞项，未定案前不启动推理层与 JEV 对齐的编码。
2. **关键路径是七步向导的端到端打通**，不是单点功能完成度。需求 12 阶段一把"跑通七步向导流程"列为第一项，顺序照此执行。
3. **每里程碑必须可验收。** 验收标准引用需求里的具体数字，不用"能用"这类描述。
4. **本机无 GPU。** 所有训练、量化、推理、延迟相关的里程碑验收必须在 GPU 机器上执行，本地只做代码级验证。相关任务在计划里显式标注 `[GPU]`。
5. **Python 版本隔离。** 训练侧固定 Python 3.11（`uv`），不用系统 3.14，理由见 `AGENTS.md`。
6. **范围受 MVP 边界约束。** 需求 10.3 明确不做的项（分布式训练、联邦、模型市场、ONNX/MNN 等）不排期。

## 0.1 当前状态（2026-10-01）

**代码已完成**：M0–M5 的全部后端与前端代码落地，460 个 Python 测试 + 94 个 TypeScript 测试全绿。

**未能验证的部分**（不是"待补测试"，是本机物理上无法执行）：

| 环节 | 状态 | 原因 |
|---|---|---|

| llama.cpp 推理与延迟 | 代码完成，**未验证** | 无 GPU；无 llama.cpp |
| 训练成功率 ≥ 95% | **无数据** | 依赖训练实测 |
| P95 / P50 / P99 / 峰值内存 | **无数据** | 依赖推理实测；且 Q1 口径未定 |

## 1. 阶段一：MVP

需求 12 给的窗口是 **1–2 个月**。当前仓库**零代码**（无 git、无工具链），因此下表按 8 周排。**【设计】** 8 周是达成需求所列全部 P0 功能的乐观估计；若要压缩，唯一可砍的是智能辅助层（见风险 R4），不是 JEV 对齐或量化链路。

### 1.1 里程碑

| 里程碑 | 周期 | 主题 | 前置 |
|---|---|---|---|
| **M0** | W1 | 仓库骨架 + 工具链 | — |
| **M1** | W1–W2 | 数据链路：治理 / 质量 / 划分 / 合成 | M0 |
| **M2** | W2–W4 | 训练链路：注册表 / 适配器 / SFT+DPO / 量化 `[GPU]` | M0、Q1 口径不影响 |
| **M3** | W3–W4 | 推理 + 评测 `[GPU]` | M2、**Q1、Q3 定案** |
| **M4** | W4–W6 | 前端七步向导 + 画布骨架 + Playground | M0 |
| **M5** | W6–W7 | 一键部署 + JEV API + 审计 | M3 |
| **M6** | W7–W8 | 端到端联调 + 反诈场景验证 + 性能达标 `[GPU]` | 全部 |

#### M1 — 数据链路（W1–W2）✅ 已完成（后端 + API）

对应需求 5.2 / 5.3 / 5.4。**前端向导页属 M4，尚未实现。**

**交付物**
- 上传（CSV / Excel / 数据库连接）、前 100 行预览、标签列智能识别（`son_data_pipeline.ingest`）
- 敏感字段自动识别与脱敏（身份证 / 手机号 / 银行卡号 / 邮箱），脱敏规则可查；**无还原路径**（`masking`）
- 质量报告：综合评分、样本量、缺失率、黑白比、异常检测、脱敏检查 + 可一键应用的建议（`quality`）
- 划分 7 : 1.5 : 1.5，三分类分层（`split`）
- 三种合成模式：`distribution_fit`（默认）/ `small_sample_derive` / `rule_injection`（`son_synth.generators`）
- 合成进度占位、保真度评分、隐私风险报告（去重 / 最近邻距离）（`son_synth.privacy`）
- API：`/api/datasets/{preview,quality,split,recommend-synth,synth}`
- 合成参数智能推荐（`recommend`）

**验收（已达成）**
- **硬约束测试**：`test` split 中 `origin == 'synth'` 的行数恒为 0（`test_split.py` 14 个用例，含一个故意注入泄漏、证明断言真的会触发的用例）
- `gray` 标签在 train/valid/test 三者中的分布偏差 < 1 个百分点
- 合成输出的每一条都带 `origin='synth'`，且**下游任何入口都无法把它写进 test split**（API 端点不接受调用方传入的划分）
- 全合成数据输入被显式拒绝，而不是悄悄改判为 train
- 测试总数：209 Python + 62 TypeScript

**实现中发现并修正的真实缺陷**（记录以免重犯）
- `text[-0:]` 是整个字符串，不是空串——邮箱脱敏（`keep_suffix=0`）因此完全失效
- 标签列检测的 coverage 分母误用行数：1500 行里 2 个标签值被算成 0% 覆盖
- 数值型业务列（`amount` 取值 1/2/3）因别名表含 `"1"→black` 被误判为标签列
- IQR 离群检测在需求 5.3 描述的形状上完全失效（离群占 31%，q3 落入离群块）；改用修正 z-score（对近 50% 污染稳健）
- 合成器在未指定 `augment_label` 时把 label 写成 `None`，产出无标签数据
- `black_white_ratio` 契约声明 `gt=0`，导致单侧样本的数据集无法构造报告；改为 `float | None`
- 测试 multipart helper 把 `files` 包了两层，所有接口测试拿到 400

**未做 / 留待后续**
- 合成进度条与 WebSocket 实时分布图（依赖 M4 前端 + M5 编排）
- Excel 与数据库连接上传：入口已留 `SourceKind.EXCEL` / `DATABASE`，读取实现待接
- SDV / CTGAN / TVAE 后端：默认用自研 Gaussian Copula（诚实标注为无相关性建模），实现 `Generator` 接口即可替换；SDV 列为 optional extra
- 保真度与最近邻距离的**阈值未定案**（技术方案 Q2），当前只报告不阻断

#### M2 — 训练链路（W2–W4）`[GPU]` 代码完成，**未验证**

> 本机无 GPU。流水线编排、超参计算、断点续训、偏好对生成全部有测试覆盖（编排层面），
> 但 `TrainingBackend` 的实际训练实现未接入，torch / PEFT / TRL 未安装，**没有任何训练数字**。

对应需求 5.5 / 5.6 / 7 / 8.1 / 8.2。

**交付物**
- 底座注册表（`registry_models`，字段对齐需求 7.1 YAML）+ 4 类底座接入：Qwen2.5-1.5B/3B-Instruct、Gemma 2 2B-it、Llama 3.2 1B/3B、自研 <1B 分类器（需求 10.2）

- 训练方法：LoRA、QLoRA、决策风格 SFT、DPO 偏好对齐（知识蒸馏/QAT/少样本迁移按资源排优先级）
- DPO 偏好数据流水线：SFT 冷启动 → 多次采样 → 正确作 chosen / 错误作 rejected
- 智能默认值：学习率、batch、step 按模型规模与数据量计算（**函数，不是常量**）

**验收**
- `format_prompt` 与 `format_jev_prompt` 在同一适配器内均可用；关闭 `jev_format_compat` 时走 `format_prompt` 而非报错
- 训练失败后可从 `checkpoints` 续训，loss 曲线不从头开始

- 4 种产物全部落模型产物卷（`SON_MODELS_DIR`），校验和与字节数入库；**模型文件不进 Git，也不进数据库列**（见 `技术方案.md` 3.0）
- `jev_compat_level` 由实测写入，**不允许人工填 L3**（需求 6.2：L3 靠对比测试验证）

**风险点**：Qwen2.5-3B + LoRA 的 12GB 显存预算是需求给的经验值，实际以 GPU 机实测为准，超了就降 QLoRA（需求 13「资源不足」对策）。

#### M3 — 推理与评测（W3–W4）`[GPU]` 代码完成，**效果指标已验证、性能指标未验证**

>
> **性能指标**（P50 / P95 / P99 / TTFT / QPS / 峰值内存）只验证了**聚合逻辑**：
> 分位数插值、TTFT 与端到端分开记录、QPS 必须有实测压测时长才计算。
> **没有任何真实延迟数字**，本机无 GPU 也无 llama.cpp。
>
> 另：Q1 未定案，P95/P99 的达标判定返回 `passed=None` 并附注说明，不静默通过或失败。

对应需求 5.7.2 / 5.7.3 / 9。

**交付物**
- llama.cpp server 编排 + FastAPI `/v1/predict` 封装
- GBNF 约束解码锁死 `output_schema` 结构
- Playground：单样本 / 从测试集随机 / 批量上传；返回 `decision/score/confidence/reason` + 响应时间
- Playground 的「判定正确 / 判定错误」→ 沉淀为偏好数据（需求 8.2 的人工来源）
- 评测引擎：**性能块**（P50/P95/P99 端到端、TTFT、QPS、峰值内存）+ **效果块**（准确率、召回率、误杀率、F1、AUC-ROC、格式合规率）+ 分标签细粒度 + 特征重要性 Top 10
- 与基线模型 / 旧版本对比
- 错误案例分析

**前置（阻塞）**：`技术方案.md` **Q1（P95 口径）** 与 **Q3（JEV 官方规范）** 必须已定案。Q1 未定案时，本里程碑只做功能不做性能达标承诺。

**验收**
- 性能指标与效果指标在 `eval_reports` 中**分字段存储**，优先级顺序为性能在前
- `gray` 标签有独立的召回/精确率，不被整体准确率掩盖
- 格式合规率 ≥ 99%（需求 9.2 / 14.2）—— 这一项在 GBNF 约束解码下应接近 100%，若不达标说明 GBNF 语法有漏洞
- 效果指标在 test split 上计算，且该 split 已通过 M1 的合成数据排除断言
- `[GPU]` 实测：P95 延迟、峰值内存 ≤ 2GB 达标情况**如实记录**，未达标就记为未达标并附实测数据，不修改目标值

## 4. 关键路径

```text
M0 骨架
 └─ M1 数据链路 ──────────────┐
 └─ M2 训练链路 [GPU] ────────┤
      └─ M3 推理+评测 [GPU] ───┤   ← Q1/Q3 阻塞点在这
                                ├─ M5 部署/JEV API
 └─ M4 前端向导 ──────────────┤
                                └─ M6 端到端验证 [GPU]
```

**最长链条：M0 → M2 → M3 → M5 → M6**，共 5 个里程碑。任何一环延期直接顺延交付日期，不并行压缩。

**M4 前端可与 M1–M3 完全并行**（依赖后端契约，而契约由 `libs/contracts` 在 M0 就固定），这是唯一有效的并行空间。

## 5. 风险登记

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| **R1** | P95 ≤ 100ms 与 `reason` 200 字符不可兼得（`技术方案.md` Q1） | **高** | **阻塞 M3/M6 验收** | 尽早在 W1 提给产品定口径；准备方案 A（reason 流式）作为默认建议 |
| **R2** | JEV 官方规范与基准集不在仓库（Q3） | 高 | 阻塞 L2/L3 验证 | W1 启动外部核实；核实前只实现 L1，**不声明 L2/L3** |
| **R3** | 8 周做完全部 P0 不现实 | **高** | 交付延期 | 唯一可砍项是智能辅助层（需求第 3 章该层），JEV 对齐与量化链路不可砍 |
| **R4** | 智能辅助层（场景识别/参数推荐/异常诊断/报告解读/智能问答）无明确实现方式（Q6） | 中 | 影响 M4 工作量 | W2 前定案：先用规则实现，不引入 LLM |
| **R5** | 反诈场景 32 字段无真实 schema（Q4） | 中 | 阻塞 M6 场景模板 | 先用需求里的示意字段，标注待替换 |
| **R6** | PyTorch/bitsandbytes 在 Python 3.14 无 wheel | 中 | 阻塞 M0 工具链 | 已用 `uv` 固定 Python 3.11 规避；W1 装依赖时立即验证 |
| **R7** | 显存估算（12GB）与实测不符 | 中 | M2 训练失败 | 预留降级路径：自动切 QLoRA 并告知用户 |
| **R8** | 各底座许可结论缺失（Q5） | 低 | 阻塞按场景过滤 | 注册表先记录 `license` 字段，法务结论后补；推荐位保守过滤 |
